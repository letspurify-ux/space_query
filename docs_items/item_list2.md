# DataGrip 대비 미구현 기능 목록 — 2차 (일반 사용자 경쟁력 관점)

작성일: 2026-08-09 · 1차 목록 [`item_list.md`](item_list.md)(항목 1~41)의 후속.

## 이 문서가 1차와 다른 점

1차는 **기능 체크리스트**였다 — "DataGrip에 있는 이 기능의 진입점이 여기 있는가".
그 방식으로 41개를 세웠고 그중 20개가 닫혔다.

2차는 **워크플로 추적**이다 — 일반 사용자가 하루를 보내는 순서(연결 → 탐색 →
작성 → 실행 → 결과 확인 → 반출 → 되돌리기)를 따라가며 *끊기는 지점*을 찾았다.
그래서 1차와 결과가 세 군데에서 갈린다.

1. **1차가 "없지만 흐름을 막지 않아 항목으로 세우지 않음"으로 뺀 것 중 둘을
   승격했다** — 실행 대상 문장 표시(42)와 상시 트랜잭션 상태 표시(50). 둘 다
   단독으로는 사소하지만 *실행 직전*과 *커밋 직전*이라는 되돌릴 수 없는 순간에
   붙어 있어서, 없을 때의 비용이 "불편"이 아니라 "잘못된 실행"이다.
2. **완료 항목의 *깊이* 부족을 처음으로 항목으로 세웠다** — 진행률·취소(46),
   표시 형식 설정(47). 1차는 진입점 유무만 봤기 때문에 "있다"로 닫혔지만, 실제로
   써 보면 큰 테이블에서 되돌릴 수 없다(46)거나 매번 같은 불만이 남는다(47).
3. **교차 스키마 탐색(43)처럼 구조에서 오는 차이를 세웠다.** 기능이 빠진 게
   아니라 트리의 뿌리가 카테고리 하나뿐이라 생기는 차이라, 기능 체크리스트로는
   보이지 않는다.

시급도 판정 기준은 1차와 같다: **(사용 빈도) x (없을 때의 우회 비용) x
(데이터 안전성 영향)**.

번호는 1차와 겹치지 않게 **42번부터** 이어 붙였다.

## Tier 0 — 시급. 되돌릴 수 없는 순간에 붙어 있는 구멍

### 42. 실행 대상 문장의 시각적 표시 (+ 문장 간 이동)

- **DataGrip**: 커서가 있는 문장이 에디터에서 옅은 배경으로 항상 표시되고,
  실행 중인 문장은 별도로 강조된다. `Ctrl+Alt+Up/Down`으로 문장 사이를 이동하고,
  `Alt+Shift+X`(Run to cursor 계열)로 여기까지만 실행할 수 있다.
- **현재 상태**: 경계 계산 자체는 이미 있다 —
  `QueryExecutor::statement_at_cursor_for_db_type_with_mysql_delimiter`
  (`src/db/query/executor.rs:1756`)가 커서 위치의 문장을 골라내고,
  `Ctrl+Enter`/`F9`가 이걸 그대로 쓴다. 문제는 **이 함수가 `Option<String>`,
  즉 텍스트만 돌려준다**는 것이다(`src/ui/sql_editor/query_text.rs:1653`).
  범위(offset)를 돌려주지 않으므로 화면에 칠할 대상이 없다. 표시 관련 심볼
  (`highlight_statement`, `current_statement_highlight`)은 소스에 없다.
  `Ctrl+Shift+Up/Down`(Select SQL Block, `menu.rs:654`)이 유일한 우회로인데,
  이건 *선택을 바꾸는* 동작이라 "확인만 하고 싶다"에 쓰기엔 부작용이 있다.
- **왜 시급한가**: 300줄짜리 스크립트에서 커서를 옮긴 뒤 `Ctrl+Enter`를 누를 때,
  **무엇이 실행될지 누르기 전에는 알 수 없다.** 주석·`/`·MySQL `DELIMITER`가
  섞이면 사람의 직관과 파서의 판정이 갈리는데, 갈렸다는 사실을 `DELETE`가 이미
  나간 뒤에 안다. 1차에서는 "흐름을 막지 않는다"고 뺐지만, 막지 않는 대신
  **틀렸을 때의 비용이 이 목록에서 가장 크다.**
- **난이도**: 중. 경계 함수를 `(start, end)`도 함께 돌려주도록 넓히는 것이
  실제 일의 대부분이고, 이건 `F9`·`Ctrl+Enter`·스크립트 실행이 공유하는
  경로라 **회귀 위험이 그쪽에 몰린다**. 칠하기 자체는 FLTK `TextDisplay`의
  하이라이트 스타일 버퍼로 가능하다(구문 강조가 이미 같은 기구를 쓴다 —
  `src/ui/sql_editor/highlighting.rs`). Run to cursor는 별도 단계로 미뤄도 된다.
- **검증**: 경계 함수는 순수 함수이므로 `(sql, cursor)` → `(start, end)` 표를
  단위 테스트로 고정한다. 기존 `statement_at_cursor*` 테스트와 **같은 입력에서
  같은 문장이 나오는지**를 대조하는 테스트가 회귀 방지의 핵심이다.

### 50. 상시 트랜잭션 상태 표시 (오토커밋 · 미커밋 변경 여부)

- **DataGrip**: 툴바에 트랜잭션 모드(Auto/Manual)가 항상 보이고, 미커밋 변경이
  있으면 커밋/롤백 버튼이 활성 상태로 바뀐다.
- **현재 상태**: 상태 바(`StatusBarWidget`, `src/ui/main_window.rs:1031`)의
  필드는 넷뿐이다 — 커넥션 표시등, 상태 텍스트, 선택 집계, 추가 건수. 오토커밋은
  **바뀔 때 지나가는 메시지로만** 보인다(`"Tab auto-commit enabled"`,
  `main_window.rs:234`). 지금 이 탭이 수동 커밋인지, 미커밋 DML이 남아 있는지는
  화면 어디에도 없다.
- **왜 시급한가**: 탭마다 커넥션과 오토커밋이 따로 놀 수 있는 제품이라
  **"이 탭이 지금 어느 모드인가"가 사용자 머릿속에만 있다.** 실수의 방향이 둘 다
  나쁘다 — 수동인 줄 알고 `UPDATE`를 날렸는데 오토커밋이었거나, 오토커밋인 줄
  알고 창을 옮겼는데 잠금이 남아 다른 세션을 막는다. 탭을 닫을 때
  `Commit and Close`(`main_window.rs:6302`)가 물어보므로 *조용히 잃는* 경로는
  없지만, 그건 마지막 방어선이지 표시가 아니다.
- **난이도**: 소. 상태 바에 프레임 하나를 더하고, 이미 존재하는 오토커밋 토글과
  트랜잭션 상태(`src/db/transaction.rs`)를 구독하면 된다. 어려운 부분은 "미커밋
  변경 있음"을 어떤 신호로 판정할지 하나로 정하는 것 — 백엔드마다 다르므로
  **클라이언트가 보낸 DML을 기준으로 하는 편**이 일관된다.
- **검증**: 상태 문자열을 만드는 순수 함수로 뽑아 (모드, 미커밋 여부, 커넥션
  유무) → 표시 텍스트 표를 테스트로 고정한다.

## Tier 1 — 중요. 매일 부딪히지만 우회는 가능

### 43. 여러 스키마를 한 트리에서 보기

- **DataGrip**: 트리의 뿌리가 *데이터 소스 → 스키마 → 카테고리*다. 여러 스키마를
  동시에 펼쳐 두고 오갈 수 있고, 어느 스키마를 볼지는 체크박스로 고른다.
- **현재 상태**: 트리의 뿌리는 **카테고리 하나**다(`root_categories`,
  `object_browser.rs:7332` — Tables/Views/...). 스키마는 트리 바깥의 스코프
  선택기로 **한 번에 하나만** 고른다(`selected_scope: Option<String>`,
  `object_browser.rs:230`, 선택기 `object_browser.rs:1236`). 다른 스키마의
  테이블을 보려면 스코프를 바꿔야 하고, 바꾸면 원래 보던 트리 상태는 사라진다.
- **왜 중요한가**: 업무 스키마와 공통/코드 스키마를 오가는 건 일상이다. 지금은
  "A 스키마의 컬럼을 보면서 B 스키마의 컬럼과 맞춰 본다"가 **불가능**하고,
  스코프를 바꿀 때마다 메타데이터를 다시 읽는다.
- **난이도**: 중~대. 트리 경로 계산·캐시 키·`qualify_object_name_for_scope`
  (`object_browser.rs:202`)가 모두 "스코프는 하나"를 전제로 한다. 다만 **캐시는
  이미 스코프별로 로드된다**(`load_metadata_cache(.., requested_scope)`)므로
  자료 구조보다 *경로 문자열과 컨텍스트 메뉴의 스키마 귀속*을 고치는 일이 크다.
- **작게 시작하는 길**: 트리 구조를 바꾸지 않고 **"최근 스코프 3개를 탭처럼
  전환"**만 넣어도 재조회 비용은 사라진다. 구조 변경은 그 뒤에 판단한다.

### 45. 결과의 총 행 수 (Count)

- **DataGrip**: 그리드 아래에 가져온 행 수가 보이고, 총 개수 버튼을 누르면
  `count(*)`를 대신 실행해 전체 건수를 알려준다.
- **현재 상태**: 테이블 브라우징 탭에는 총계가 있다 —
  `SELECT COUNT(*) AS SQ_TOTAL_ROWS FROM {}`(`src/ui/table_browse.rs:336`)로
  페이징을 계산한다. **일반 쿼리 결과에는 이 경로가 없다.** 상태 바의 추가 건수
  (`additional_count`, `main_window.rs:1039`)는 *지금까지 가져온* 행이지 총계가
  아니다.
- **왜 중요한가**: 지연 fetch가 기본이라 "1,000행 표시"가 총계인지 잘린 것인지
  화면만 봐서는 구분되지 않는다. 확인하려면 에디터로 돌아가 쿼리를
  `SELECT COUNT(*) FROM (...)`로 감싸 다시 실행해야 한다 — 1번 항목(필터
  재조회)이 이미 만든 **파생 테이블 래핑 파이프라인과 똑같은 일**이다.
- **난이도**: 소. 1번의 래핑 로직에 집계만 갈아 끼우면 된다. 게이트도 1번과
  같다(재조회 불가능한 결과에는 제공하지 않는다).

### 46. 긴 작업의 진행률과 취소 (Export · Import · Fetch All)

- **DataGrip**: 내보내기/가져오기가 진행률 표시줄과 취소 버튼을 단 백그라운드
  작업으로 돈다.
- **현재 상태**: 진행률 기구는 **이미 있다** — `DbActivityProgress::Determinate`
  를 객체 트리 갱신(`object_browser.rs:2361`)과 메인 윈도우
  (`main_window.rs:1433`)가 쓴다. 그런데 **내보내기 경로는 이걸 쓰지 않는다**:
  `render_table_export`(`object_browser.rs:5937`)는 `QueryResult` 전체를 받아
  한 번에 문자열로 렌더한다. `cancel_export`류 심볼도 없다. 임포트
  (`src/ui/table_import.rs`)와 "전체 행 내보내기"의 선행 fetch
  (`LazyFetchPendingAction::Export`)도 마찬가지다.
- **왜 중요한가**: 1차가 26번을 닫으면서 "큰 테이블에서 되돌릴 수 없다"고
  적어 뒀는데, 같은 성질이 **3번(임포트)·2번(내보내기)에도 똑같이 있다**.
  100만 행 테이블을 실수로 내보내기 시작하면 끝날 때까지 앱이 잡혀 있다.
  기능이 없는 게 아니라 **쓰기 무서운 상태**라는 점에서, 없는 기능보다 나쁘다.
- **난이도**: 중. 어려운 건 UI가 아니라 **렌더러를 스트리밍으로 바꾸는 것**이다.
  `result_export::render`가 전체를 받아 전체를 돌려주는 순수 함수라(그래서
  테스트가 쉬웠다) 청크 단위 API가 하나 더 필요하다. 취소는 기존 취소 2단 모델
  (`session_policy`)과 같은 계약을 쓰면 된다.
- **작게 시작하는 길**: 취소부터. 진행률 없이 "취소" 하나만 있어도 되돌릴 수
  없는 상태는 사라진다.

## Tier 2 — 있으면 확실히 낫다. 흐름을 막지는 않음

### 44. 객체 트리 즉시 검색 (타입어헤드 / 필터 입력)

- **DataGrip**: 트리에 포커스를 두고 글자를 치면 즉시 좁혀진다(speed search).
- **현재 상태**: 트리의 키 처리에 문자 입력 경로가 없다(`object_browser.rs`에
  `event_text()` 기반 타입어헤드 없음). 대신 **`Ctrl+Shift+N` Go to Object**
  (10번, 완료)가 있어서 이름을 아는 경우는 이미 해결된다.
- **판정**: Go to Object가 있으므로 Tier 2. 다만 "이름 일부만 기억나고 트리에서
  훑고 싶다"는 흐름은 아직 없다.
- **난이도**: 소. 트리 항목 목록은 이미 메모리에 있다.

### 47. 결과 표시 형식 설정 (NULL 텍스트 · 날짜 · 숫자)

- **DataGrip**: 설정에서 NULL 표시 문자열, 날짜/시각 포맷, 숫자 표기, 무한/NaN
  표시를 정한다.
- **현재 상태**: NULL 텍스트는 상수 `DEFAULT_NULL_TEXT = "NULL"`
  (`result_table.rs:864`)이고 `set_null_text`(`result_table.rs:11067`)는 있지만
  **사용자 설정이 아니라 SQL\*Plus `SET NULL`이 바꾸는 값**이다. 날짜·숫자 표시
  형식 설정은 없다(`display_format`·`number_format` 없음) — 세션 NLS에 그대로
  묶인다. 설정 창(`settings_dialog.rs`)의 탭은 Editor/Results 둘, 그룹은 Font ·
  Result View · IntelliSense · Connection · SQL Formatting뿐이다.
- **왜 필요한가**: NULL과 빈 문자열이 화면에서 구분되지 않으면 편집·내보내기
  판단이 흔들린다. 다만 **내보내기 쪽은 이미 포맷의 어휘를 따르도록 정해져
  있어**(2번 항목) 피해가 표시로 한정된다.
- **난이도**: 소(NULL 텍스트) ~ 중(날짜/숫자 — 값이 전부 문자열이라 역파싱이
  필요하고, 이건 1번 항목에서 **로컬 필터를 접었던 바로 그 이유**다). **NULL
  텍스트만 설정으로 빼고 날짜/숫자는 손대지 않는 편**을 권한다.

### 48. FK 값 선택 도우미 (참조 테이블에서 값 고르기)

- **DataGrip**: FK 컬럼을 편집할 때 참조 테이블의 값 목록에서 고를 수 있다.
- **현재 상태**: 편집 경로(`src/db/result_edit.rs`, `result_table.rs`)에 FK 개념이
  전혀 없다(`foreign` 문자열 없음). 13번(관련 데이터 이동)·32번(FK JOIN 완성)과
  **같은 메타데이터 한 벌**을 쓴다.
- **난이도**: 중. 셋을 묶어 "FK 메타데이터 로더" 하나를 먼저 만들면 13·32·48이
  같이 열린다. 반대로 따로 하면 세 번 조회한다.

### 49. 커넥션 프로파일 복제 · 순서 · 그룹

- **현재 상태**: 커넥션 대화상자는 이미 넓다 — 이름/호스트/포트/서비스, Color,
  Safety, SSL, Isolation, Access, 시간대, Test, Delete
  (`connection_dialog.rs:1143`~`1409`). 없는 것은 **복제**
  (`duplicate_connection` 없음), **순서 바꾸기**, **폴더/그룹**이다.
- **왜 필요한가**: dev/stage/prod처럼 한 글자만 다른 프로파일을 만들 때마다
  전부 다시 입력한다. 11번(색상)으로 구분은 되지만 **만드는 비용**은 그대로다.
- **난이도**: 소. 복제만이라도 즉시 값어치가 있다.

### 51. 그리드 행 번호로 이동 / 행 탐색

- **현재 상태**: 행 헤더는 있다(`table.set_row_header(true)`,
  `result_table.rs:2429`). 이동 수단이 없다(`go_to_row` 없음).
  `Ctrl+Arrow`로 끝까지, 11-b의 `Ctrl+F`로 텍스트 검색은 된다.
- **판정**: `Ctrl+F`가 대부분을 흡수하므로 Tier 2 하위. 에디터의 Go to Line(28번,
  완료)과 대칭이라 만들기는 쉽다.

### 52. 그리드 컬럼 헤더 전용 메뉴

- **현재 상태**: 헤더에서 우클릭하면 **선택 영역 메뉴가 그대로** 뜬다
  (`context_menu_hit_accepts_column_header_and_empty_column_body`,
  `result_table.rs:16441`). 그 안에 컬럼 단위 동작은 `Columns...`(6번) 하나뿐이다.
  컬럼 이름 복사, 이 컬럼만 정렬/숨김, 이 컬럼 기준 필터는 헤더에서 못 한다.
- **난이도**: 소. 동작 자체는 24·25·6번이 이미 다 갖고 있고, **헤더 히트일 때
  메뉴 항목만 갈아 끼우면** 된다. 값 대비 비용이 이 목록에서 가장 좋다.

## Tier 3 — 범위 밖이거나 제품 결정이 필요

### 53. 결과 비교 · 결과를 파일로 직접 실행

두 결과를 나란히 비교(`diff_result` 없음), 쿼리 결과를 그리드를 거치지 않고
파일로 바로 흘려보내기(execute-to-file) 둘 다 없다. 17번(스키마/데이터 비교)과
46번(스트리밍 내보내기)이 각각 선행이라 지금 세울 항목이 아니다.

### 54. 추가 DB 지원 (PostgreSQL · SQLite · SQL Server)

**"일반 사용자 관점에서 DataGrip과 경쟁"이라는 기준을 그대로 적용하면, 이 목록
전체를 통틀어 가장 큰 격차는 이것이다.** DataGrip을 사는 사람의 상당수는
"쓰는 DB가 여러 개라서" 산다. 1차는 이걸 "제품 포지셔닝 결정"으로 분류해
Tier 3에 두었고(21번), 그 판단 자체는 유효하다 — 다만 **기능 목록을 아무리
채워도 이 항목을 열지 않으면 경쟁 구도가 "DataGrip 대신"이 아니라 "Oracle/MySQL
전용 대안"으로 고정된다**는 사실은 목록에 적혀 있어야 한다.

지금 구조가 이 결정에 유리한 편이라는 점은 기록해 둘 만하다: 백엔드별 차이가
`object_browser_behavior_for`(`object_browser.rs:594`),
`session_policy`, `result_messages` 같은 **디스패치 지점 몇 개로 이미 모여
있다**. 새 백엔드의 비용은 UI가 아니라 드라이버와 메타데이터 쿼리 쪽이다.

**이건 구현 항목이 아니라 결정 항목이다.** 결정 전에는 42~52를 진행하는 편이
어느 쪽으로 결정하든 손해가 없다.

### 그 밖에 (없음을 확인했지만 항목으로 세우지 않음)

코드 폴딩(1차 28번), 인쇄, SQL 파일 인코딩 선택, 트리의 시스템 객체 표시 토글
(`show_system` 없음), 북마크(`bookmark` 없음), 에디터 분할 뷰(`split_editor`
없음), 클립보드에서 표 붙여넣어 임포트(`import_from_clipboard` 없음),
자동 새로고침(`auto_refresh` 없음). 전부 없는 것을 확인했고, 각각이 독립적으로
흐름을 막지 않는다.

## 이 목록의 한계 (검토 요청)

- **판정 방식은 1차와 같다 — 소스에서 진입점(문자열·심볼·핸들러)이 있는지만
  봤다.** "없다"는 확실하지만 **"만드는 비용"은 전부 추정**이다. 특히 43번(교차
  스키마)과 46번(스트리밍 내보내기)은 기존 전제를 넓히는 일이라 추정보다 커질
  수 있다.
- **42번과 50번은 1차가 의도적으로 뺀 것을 되살린 것이다.** 1차의 "흐름을 막지
  않는다"는 관찰은 맞다. 내가 바꾼 것은 관찰이 아니라 **가중치** — 데이터
  안전성 축을 빈도보다 무겁게 봤다. 이 가중치에 동의하지 않으면 둘 다 Tier 2로
  내려가는 게 맞고, 그건 제품 결정이다.
- **46번과 47번은 "미구현"이 아니라 "얕음"이다.** 완료로 닫힌 항목을 다시 여는
  형태라 목록의 성격이 1차와 다르다. 닫힌 항목을 재평가할 생각이 없다면 이 둘은
  빼도 목록이 성립한다.
- **54번(추가 DB)은 내가 순위를 매길 수 있는 항목이 아니다.** "경쟁"이라는
  기준을 문자 그대로 적용했을 때 가장 크다는 사실만 적었다.
- 2차 조사에서 **UI를 띄워 확인한 것은 없다.** 전부 소스 판독이다. 특히 52번의
  "헤더 우클릭이 선택 메뉴를 그대로 띄운다"는 테스트 이름
  (`result_table.rs:16441`)에서 읽은 것이라, 실제 화면에서 한 번 확인하는 편이
  좋다.
